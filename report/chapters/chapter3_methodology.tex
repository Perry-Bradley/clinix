\chapter{MATERIALS AND METHODS USED}

\section{Introduction}

This chapter outlines the development methodology, system analysis, and design approaches for the Clinix platform. It details the tools, technologies, and processes employed throughout the project life-cycle, from requirements gathering to system design.

\section{Methods Used}

\subsection{Development Methodology}

Clinix employs an \textbf{Agile-Scrum hybrid methodology} adapted for academic project constraints:

\begin{itemize}
  \item \textbf{Sprints:} Two-week development cycles with specific deliverables.
  \item \textbf{Backlog Management:} Prioritised feature implementation based on core functionality.
  \item \textbf{Documentation:} Continuous documentation aligned with academic requirements.
  \item \textbf{Testing Integration:} Test-driven development within each sprint.
\end{itemize}

This approach balances the flexibility of Agile with the structured milestones required for academic supervision.

  \item \textbf{Provider Verification Module:} Credential submission, superadmin review, status updates.

  \item \textbf{Consultation Module:} AI chatbot interface, video/audio calling, secure messaging, and prescription generation.

  \item \textbf{Health Records Module:} Basic medical history, consultation records, and medication tracking.
  \item \textbf{Payment Module:} Mobile-money integration (MTN Mobile Money, Orange Money via CamPay) and transaction history.
  \item \textbf{Administrative Module:} User management, analytics, reporting, and verification dashboard.
  \item \textbf{Notification System:} Appointment reminders, consultation updates, security alerts.
  \item \textbf{AI Diagnostic Engine:} Symptom analysis, preliminary assessment, escalation protocols.
  \item \textbf{Home-Care Module:} Lab-test bookings and home-treatment bookings delivered by verified nurses.
\end{itemize}

\subsubsection{Functional Requirements}

\begin{itemize}
  \item The system shall allow patients to register using phone-number or email verification.
  \item The system shall enable healthcare providers to submit credentials for verification.
  \item The system shall support appointment scheduling with available time-slot detection.
  \item The system shall provide AI-powered symptom checking with escalation to human providers.
  \item The system shall integrate real-time video/audio calling using WebRTC technology.
  \item The system shall display nearby healthcare providers on an interactive map.
  \item The system shall generate and store consultation records securely.
  \item The system shall process payments through mobile-money integration.
  \item The system shall send automated notifications for appointments and updates.
  \item The system shall provide analytics to superadmins for platform monitoring.
\end{itemize}

\subsubsection{Non-functional Requirements}

\begin{itemize}
  \item \textbf{Performance:} App loading time $<$~3 seconds; video-call latency $<$~200~ms.
  \item \textbf{Security:} End-to-end encryption for consultations, JWT-based authentication, secure credential storage, compliance with Cameroonian data-protection laws.
  \item \textbf{Usability:} Intuitive navigation, support for English and French, accommodation of varying digital literacy.
  \item \textbf{Reliability:} 99\% uptime for critical services and graceful degradation during connectivity issues.
  \item \textbf{Scalability:} Support for at least 100 concurrent users and modular architecture for feature addition.
  \item \textbf{Maintainability:} Clean code structure, comprehensive documentation, modular feature-based design.
\end{itemize}

\subsubsection{Activity Diagrams}

The Clinix activity diagram (Figure~\ref{fig:activity}) maps two parallel user workflows that converge during consultations.

\begin{itemize}
  \item \textbf{Healthcare Providers} follow a path of registration $\rightarrow$ credential submission $\rightarrow$ payment $\rightarrow$ verification (leading to either approval or rejection).
  \item \textbf{Patients} follow registration/login $\rightarrow$ symptom entry $\rightarrow$ AI analysis $\rightarrow$ decision point. If provider consultation is needed, they search for nearby providers $\rightarrow$ book appointments $\rightarrow$ attend virtual consultations (via mobile-money payment) $\rightarrow$ view consultation summaries with AI recommendations.
\end{itemize}

The diagram uses merge and join nodes to show how these separate workflows synchronise, particularly when patients and providers connect during consultations. This design ensures the system handles multiple concurrent user paths while maintaining smooth user experiences and efficient service delivery.

The Clinix system class diagram (Figure~\ref{fig:class}) shows an object-oriented healthcare platform with three main user types inheriting from a base \texttt{User} class: \textbf{Patient} (can request consultations and view records), \textbf{HealthcareProvider} (manages credentials and conducts consultations), and \textbf{Superadmin} (verifies providers and manages the system).

The relationships show patients and providers connecting through appointments, which lead to consultations that generate medical records. The design emphasises role-based access control, maintainability, and clear separation between clinical workflow and AI-learning components.

\subsubsection{Sequence Diagrams}

The sequence diagram (Figure~\ref{fig:sequence}) shows a patient-consultation workflow starting when a patient enters symptoms into the mobile app. The \textbf{AI Consultation Engine} (Google Gemini, accessed server-side through the Django API) analyses the conversation turn by turn, optionally taking attached images into account, and returns a final structured assessment containing a summary, a triage priority, a recommended medical specialty, possible causes, and red-flag indicators.

If professional help is needed, the \textbf{Provider Recommender} consumes the recommended specialty from the AI assessment together with the patient's location, language preference, and consultation-fee budget, and returns a ranked list of verified providers. The patient picks one and the \textbf{Django API} schedules an appointment, notifies the provider, and stores details in \textbf{PostgreSQL}. After the virtual consultation, the provider creates a diagnosis or prescription that is saved as a medical record.

The diagram emphasises that all AI processing happens against a pre-trained external model: Clinix does not train or fine-tune any model locally. Privacy is preserved by never persisting patient identifiers in the AI prompt and by storing structured assessments rather than raw conversation transcripts beyond their session lifetime.

\subsubsection{System Architecture}

Clinix adopts a \textbf{three-tier architecture}:

\begin{itemize}
  \item \textbf{Presentation Tier:} Flutter mobile applications (patient \& provider modes in a single codebase) and a React-based admin dashboard.
  \item \textbf{Application Tier:} Django REST API handling business logic, authentication, and service integration; supplemented by Django Channels (WebSocket) and Celery (asynchronous tasks).
  \item \textbf{Data Tier:} PostgreSQL database with encrypted sensitive data, Redis cache for performance and message broker, and Firebase Cloud Storage for media and call recordings.
\end{itemize}

\subsubsection{Database Architecture}

The Clinix database uses a distributed architecture with three storage layers coordinated by the \textbf{Django REST API} (which serves both the Flutter mobile app and the React web admin):

\begin{itemize}
  \item \textbf{PostgreSQL} --- primary relational database storing structured data (users, patients, providers, appointments, consultations, medical records, payments).
  \item \textbf{Redis} --- in-memory store used as a cache for frequently accessed data, as the channel layer for Django Channels (WebSocket), and as the broker for Celery tasks.
  \item \textbf{Cloud Storage} --- handles large files like medical images, KYC documents, and call-recording audio with scalable, secure storage.
\end{itemize}

\subsubsection{AI Provider Recommendation Architecture}

Clinix integrates a pre-trained, general-purpose multimodal large language model (Google Gemini) and uses it as a clinical-reasoning layer that turns a free-form symptom conversation into a structured, machine-readable recommendation. The platform reasons only with what the patient explicitly shares in a single session, and what survives the session is a small structured assessment rather than the raw conversation transcript.

\paragraph{Architecture Components}
The recommendation pipeline consists of four cooperating components:

\begin{itemize}
  \item \textbf{AI Consultation Session.} A server-side conversation, identified by an \texttt{AISymptomSession} record, in which Gemini and the patient exchange messages (optionally with attached images). The patient's most recent vitals (heart rate, HRV, respiratory rate, daily activity) are injected silently as context so that the model can reason over physiological state without alarming the patient.
  \item \textbf{Structured Assessment Generator.} A dedicated end-of-session call (\texttt{POST /api/v1/ai/chat/<id>/complete/}) that asks Gemini to return a JSON object containing a summary, a triage priority (Low/Medium/High), a recommended medical specialty, two to five possible causes, and a red-flag boolean. This object is the contract between the AI layer and everything downstream.
  \item \textbf{Provider Recommender.} A scoring service backed by \texttt{GET /api/v1/providers/recommended/} that consumes the recommended specialty from the assessment and filters only \texttt{approved} verified providers. Each candidate is scored on specialty match, rating, years of experience, haversine distance from the patient's location, language overlap with \texttt{User.language\_pref}, consultation fee versus the patient's budget, and recent online status (\texttt{last\_seen} within five minutes).
  \item \textbf{Transparent Ranked Output.} The top providers are returned to the mobile app together with human-readable \texttt{match\_reasons} (e.g.\ ``General practitioner online now, 1.2~km from you, speaks English and French''), so the patient understands why each option appears.
\end{itemize}

A mid-session shortcut also exists: \texttt{POST /api/v1/ai/chat/<id>/recommend/} returns a provider recommendation \emph{without} closing the session, so the AI can suggest a doctor while the patient is still describing symptoms.
